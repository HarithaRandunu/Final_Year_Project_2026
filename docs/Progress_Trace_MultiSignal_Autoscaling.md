**The blocker this phase is built around: Module 2 cannot work on EKS as it stands.** It is a scheduler *extender*, wired on kind by `docker cp`-ing a replacement `kube-scheduler` static-pod manifest into the control-plane container (`ablation/run_trial.py::set_scheduler_mode`). EKS's control plane is fully managed — no node to exec into, and `kube-scheduler` cannot be given a config. The fix in `project/eks/module2_scheduler/` runs the `kube-scheduler` binary as an in-cluster Deployment with our own `KubeSchedulerConfiguration`, selected per workload via `spec.schedulerName`. **`module2_extender/app.py` is unchanged.** Four differences from the kind config, all load-bearing:

1. **`profiles[].schedulerName: module2-scheduler`** — the one that is easiest to miss. A scheduler acts only on Pods matching a profile it declares, and the default profile name is `default-scheduler`; without this block ours would claim the same name as AWS's and the two would race to bind every pod in the cluster, silently.
2. **No `clientConnection.kubeconfig`** — that path (`/etc/kubernetes/scheduler.conf`) exists only on a control-plane node; an in-cluster scheduler uses its ServiceAccount token.
3. **`leaderElect: false`** — single replica, and the default lease is the one the managed scheduler uses.
4. **DNS `urlPrefix` instead of a hard-coded ClusterIP** — and this *removes* a fragile step: the ClusterIP was hard-coded only because kind's scheduler is a host-network static pod with no cluster DNS, which is why `live_cluster/README.md` has to grep the live ClusterIP and rewrite the file each rebuild.

**Node sizing corrected during this work, from the real manifests rather than an estimate.** An earlier suggestion of 4 × `t3.medium` is **wrong** and would have broken the experiment: TeaStore at one replica each is 7.25 GiB, the framework 0.56 GiB, supporting services ~1.5 GiB, and five extra `teastore-webui` replicas add 7.5 GiB → **~16.8 GiB at `maxReplicas=6`**, against only ~12.8 GiB allocatable on 4 × t3.medium after EKS node overhead. Scale-up would have stalled on Pending pods — destroying the exact measurement the cluster exists to take. **4 × `t3.large`** (~28 GiB allocatable). The node group is deliberately fixed (`minSize == maxSize == 4`, no cluster autoscaler): a node set that changes under Module 2's bandit invalidates its posteriors mid-experiment.

**Second correction: the Phase 6 load rates are too low for this cluster.** Phase 6 validated 8–24 req/s against 2 kind nodes at `maxReplicas=2`, kept deliberately conservative because of the laptop's documented OOM history. Four t3.large nodes at `maxReplicas=6` have roughly 3–4× that capacity, so the same rates would be absorbed with no scaling and no violations — reproducing Phase 6's inconclusive results on hardware that costs money. `project/eks/loadgen/capacity_probe.js` therefore takes its rates from an env var (the kind version hardcodes 8/16/24) so the saturation point can be swept for; its default `25,50,100,150,200` is an explicit **guess, not a validated band**. Finding the real number is a required step, not an optional one.

Also noted: `ignorable: true` in the extender config (carried over from kind, and correct — an extender outage should degrade Module 2, not wedge the cluster) means **a silently dead extender looks exactly like a working `m2` arm**. The go/no-go check therefore requires reading the extender's own log for `/filter` and `/prioritize` hits, not just observing that pods schedule.
